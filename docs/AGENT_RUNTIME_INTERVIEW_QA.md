# 企业级 Agent Runtime：100 题面试问答

> 基于项目描述整理。回答以第一人称口述为主；字段名或实现细节应在面试前结合真实代码复核。

## 一、项目与架构（1—20）

1. **项目解决什么问题？** 传统 Agent 多是一次性模型调用，长任务中断、工具副作用和最终交付都缺少可靠状态。我将其升级为可恢复、可追溯、可评测、可治理的 Agent Runtime。
2. **什么是企业级 Agent Runtime？** 它不只负责模型编排，还负责执行状态、证据、评测、权限和发布；模型只是其中的决策组件。
3. **目标用户是谁？** 一线开发者需要长程编码和评审，业务协作者需要 IM 交付，管理员需要权限、审计和发布治理。
4. **三类场景为何共用 Runtime？** 都是多轮、多工具、可能中断且有外部副作用的任务；差异放在 Skill、Policy 和 DeliveryReceipt。
5. **三类场景差异？** 编码关注文件与测试，评审关注证据与风险，IM 关注身份、权限和消息幂等。
6. **北极星指标？** 可靠交付率：任务在恢复、重试或人工确认后，能以完整证据产出无重复副作用交付物的比例。
7. **为何强调四个“可”？** 可恢复保证可用，可追溯保证可信，可评测保证迭代安全，可发布保证企业治理。
8. **只能先做两个选什么？** 可恢复和可追溯。前者解决长任务可用性，后者解决企业是否敢授权 Agent 执行。
9. **和 LangGraph 的区别？** LangGraph 更偏开发编排；项目重点是生产运行时，包括持久化执行、证据、评测、发布和治理。
10. **核心个人贡献？** 我把 Agent 抽象为 ExecutionRun 驱动的执行系统，并串起 Checkpoint、Tool Ledger、评测和交付治理。
11. **用户工作流变化？** 从“中断后重新问、过程不可见”变成“可查看执行、恢复任务、追溯证据和确认交付”。
12. **为何不是功能堆砌？** 所有能力围绕同一对象 ExecutionRun：恢复、证据、评测、发布都服务可靠交付。
13. **没有大规模流量如何评估？** 用历史 trace 回放、故障注入和高风险路径验证；项目覆盖 63 个 Session、307 次工具调用。
14. **ROI 怎么讲？** 上下文从 515.3 万降至 20.7 万字符，减少 96%；同时减少人工重跑和治理事故成本。
15. **不适合什么场景？** 极短、无工具、无副作用的普通问答，直接模型调用更轻量。
16. **最大技术债？** 外部非幂等副作用的不确定性，例如消息可能已发出但本地超时；需结合回执、幂等键和人工确认。
17. **再给三个月做什么？** 分布式取消/接管、生产 trace 自动生成评测 case、细粒度策略审批。
18. **IM 为什么更需治理？** 消息会被视为组织行为，必须记录身份、授权、接收方、送达回执和脱敏结果。
19. **平台与业务策略如何划分？** Runtime、证据、恢复、评测是平台；轮数、工具白名单、风险阈值是业务策略。
20. **如何避免过度抽象？** 只抽象跨场景稳定对象，如 Run、Checkpoint、Evidence；特定业务规则放到 Skill/Policy。

## 二、执行链路与工具（21—40）

21. **三层职责？** AgentSession 管生命周期和身份；ConversationRunner 管轮次和模型决策；ToolManager 管工具注册、权限、参数与执行。
22. **为何分层？** 将会话、推理、工具副作用隔离，便于替换模型、恢复 Run 和独立审计工具。
23. **层间协议？** Runner 消费 Session 上下文并输出 action；ToolManager 返回结构化 receipt；Run 持久化状态转换。
24. **Session 生命周期？** 创建、绑定会话、创建多个 Run、归档；Session 不等于单次执行。
25. **Session 与 Run 的关系？** 一个 Session 可有多个 Run；Run 是一次可恢复执行尝试。
26. **Runner 如何管理上下文？** 模型侧只保留必要摘要与 evidence 引用，完整工具输出外置。
27. **ToolManager 做什么？** 发现工具、校验 schema、鉴权、执行、超时控制、幂等和写 Tool Ledger。
28. **工具失败谁处理？** ToolManager 产出标准错误 receipt；Runner 决定重试、降级、询问用户或结束。
29. **模型参数非法怎么办？** 先 schema 校验，不执行副作用；将可修复错误反馈给 Runner，限制修复轮数。
30. **如何避免死循环？** Run 记录轮次、工具调用指纹和状态；达到 10 轮或重复策略阈值强制退出。
31. **10 轮怎么定？** 由历史任务收敛情况、成本和失败模式确定，并保留按 Skill 覆盖的策略入口。
32. **达到上限如何处理？** Run 标记为需恢复/人工确认，输出已完成证据和未完成原因，而非伪造成功。
33. **工具成功但业务失败如何区分？** receipt 分开记录 transport 成功、业务状态码和可验证产物。
34. **如何关联请求与交付？** 用 run_id、tool_call_id、evidence_ref、delivery_receipt_id 贯穿。
35. **如何支持流式？** 文本 token 走流式通道，工具状态走结构化事件；最终统一落入 Run trace。
36. **如何并行工具？** ToolManager 按工具的并发/依赖策略创建子节点，合并 receipt 后交回 Runner。
37. **长耗时工具怎么做？** 异步 job + 心跳/轮询 + Checkpoint，不阻塞 Runner 线程。
38. **超时如何判断远端是否成功？** 不把超时直接当失败；查询幂等键或远端 receipt，状态不明时进入人工确认。
39. **如何防重复发消息？** 每个有副作用调用携带业务幂等键，Tool Ledger 在投递前后记录请求与回执。
40. **哪些状态必须持久化？** Run 状态、节点状态、Checkpoint、工具 receipt、证据引用、权限决策和交付回执。

## 三、恢复与证据（41—60）

41. **ExecutionRun 关键字段？** run_id、session_id、状态、当前节点、轮次、输入摘要、模型/Skill 版本、创建和恢复时间。
42. **Checkpoint 保存什么？** 保存下一步恢复所需的计划、已完成节点、工具 receipt 引用和模型摘要，不复制全部原始输出。
43. **何时写 Checkpoint？** 节点开始、外部副作用提交前后、关键状态转移和退出前。
44. **为何不只存消息历史？** 消息无法可靠表达节点执行、幂等键和外部副作用状态。
45. **如何恢复？** 读取最后一致 Checkpoint，跳过已完成且 receipt 可验证的节点，从可重试节点继续。
46. **如何防止恢复重复执行？** 节点状态和工具幂等键双重判断；实验中 10 轮退出恢复的重复完成节点数为 0。
47. **重复执行数如何统计？** 按同一 run、节点语义和幂等键聚合，已完成节点再次成功执行即记重复。
48. **工具已成功但未落库怎么办？** 查询外部回执；可确认则补写 Ledger，不可确认则标记 uncertain 并人工处理。
49. **Checkpoint 写失败怎么办？** 不推进可恢复状态；对副作用工具采用提交前/后双 checkpoint 和补偿查询。
50. **如何处理状态不一致？** 以可验证的外部 receipt 为事实源，Checkpoint 是恢复索引，不是唯一真相。
51. **何时人工恢复？** 权限过期、外部副作用不确定、风险操作需审批或证据缺失时。
52. **模型版本变了还能恢复吗？** 恢复使用 Run 固化的模型/Prompt/Skill 版本；若不可用则创建新的可比较 Run。
53. **如何防并发恢复？** 使用 Run lease、乐观版本号或分布式锁，只有持有者可推进节点。
54. **为何需要状态机？** 让 pause/cancel/retry/recover 有合法迁移，避免任意覆盖状态。
55. **Raw Evidence 存什么？** 原始工具输出、代码 diff、测试日志、远端回执等不可篡改事实。
56. **Tool Ledger 和日志区别？** Ledger 是结构化、可关联、可审计的业务事实；普通日志只是排障记录。
57. **Task Canvas 是什么？** 面向模型和用户的任务工作面，保留目标、计划、进度、摘要和证据引用。
58. **为何完整输出外置？** 防止长任务上下文膨胀；项目将 515.3 万字符降到 20.7 万字符。
59. **如何避免摘要失真？** 摘要必须保留 evidence 引用，关键结论按需回读原始证据。
60. **敏感证据怎么处理？** 原文按租户和权限存储，摘要/引用做脱敏，模型仅拿最小必要内容。

## 四、评测与治理（61—80）

61. **评测链路是什么？** trace → episode → case → replay → verifier → scorecard。
62. **为何评测 trace？** 最终答案正确不代表过程安全；trace 能发现重复工具、越权、错误恢复。
63. **episode 如何划分？** 以一个用户目标及其执行闭环为边界，可包含多轮和多个工具节点。
64. **case 来源？** 历史 trace、线上事故、高风险场景和人工设计的负对照。
65. **replay 如何稳定？** 对外部工具采用录制 receipt 或 Mock，隔离环境变化。
66. **verifier 如何避免自评偏差？** 采用规则、可验证 receipt 和跨模型 verifier 结合，而非只让生成模型自评。
67. **scorecard 指标？** 完成度、证据一致性、工具安全、恢复正确性、成本、时延和交付质量。
68. **假通过问题是什么？** 测试命令未真正执行但退出码为 0，导致流水线把空跑当通过。
69. **如何修复？** 校验测试发现数量、收集结果、关键断言和报告产物，负对照确保失败能使流水线失败。
70. **10 类故障包含什么？** 工具超时、网络中断、重复投递、checkpoint 异常、权限失效、恢复冲突等。
71. **高风险路径是什么？** 远程 Skill、跨租户、脱敏、发布回滚和有副作用工具路径。
72. **如何把线上失败变 case？** 从 trace 提取输入、策略版本、receipt 与失败断言，脱敏后进入回放集。
73. **如何防评测过拟合？** 按时间和租户切分，保留未见故障集，定期从新 trace 补充样本。
74. **模型升级怎么回归？** 固定 case/replay，比较 scorecard、成本和风险指标，并设置发布门槛。
75. **身份如何统一？** 四类入口都映射为统一 principal、tenant、role 和 scope。
76. **远程 Skill 怎么治理？** 白名单、签名/版本、最小权限、网络限制、审计和一键回滚。
77. **Skill 发布流程？** 测评通过→灰度发布→监控→正式发布；异常时回滚到已验证版本。
78. **DeliveryReceipt 是什么？** 最终交付的结构化回执，说明产物、证据、接收方、状态和确认结果。
79. **跨租户如何隔离？** 每个查询、Evidence、Skill、工具凭证和缓存 key 都带 tenant 边界并做回归验证。
80. **24/24 治理回归说明什么？** 覆盖的权限、脱敏、远程 Skill、隔离和回滚路径均按预期拒绝或放行。

## 五、深挖与总结（81—100）

81. **最难的设计选择？** 将工具输出从对话上下文中移出，同时保证模型仍能按引用获取足够证据。
82. **证据分层的收益？** 降低 96% 上下文字符量，同时保留可审计、可回读的事实来源。
83. **最大风险？** 外部副作用的“不确定完成”；必须显式建模，而非简单重试。
84. **如何做取消？** Run 进入 cancelling，阻止新节点；可取消工具发送取消信号，不可取消工具等待 receipt 后做补偿。
85. **如何做成本治理？** 每个 Run 记录模型 token、工具耗时和重试成本，按 Skill/租户设预算。
86. **如何做限流？** 按 tenant、用户、Skill、工具和并发 Run 设配额，超过时排队或降级。
87. **如何做安全审批？** 高风险 Tool Policy 返回 approval_required，Checkpoint 保留上下文，审批后从原节点恢复。
88. **模型幻觉如何治理？** 结论必须可引用 Evidence；没有足够证据时输出不确定性和下一步建议。
89. **为什么不是纯工作流引擎？** 工作流引擎不解决模型决策、上下文压缩、证据引用和模型评测；Runtime 同时覆盖二者。
90. **为什么不是纯 observability？** 可观测只记录发生了什么；Runtime 还负责恢复、重放、治理和交付。
91. **如何支持新工具？** ToolManager 统一 schema、权限、幂等、timeout 和 receipt 协议，新工具实现适配器即可。
92. **如何支持新入口？** 将入口适配为统一身份和交付协议，不让飞书、微信、Dashboard 各自实现 Agent 状态。
93. **如何做代码审查质量验证？** 用历史 PR/review trace 回放，对风险命中、证据引用、误报和漏报评分。
94. **如何处理 Prompt 注入？** 将外部工具内容标为不可信 Evidence，禁止其改变系统策略或直接触发高风险工具。
95. **如何处理隐私删除请求？** 根据 tenant 和 evidence 索引定位原文、摘要、缓存、Ledger 引用，执行可审计删除或不可逆脱敏。
96. **如何保证审计日志可信？** 将关键 receipt、权限决策和版本信息以追加式记录保存，并限制修改权限。
97. **项目失败时如何复盘？** 以 trace 为单位复盘：输入、策略、节点、工具 receipt、证据、恢复与交付，而非只看最终文本。
98. **如何向非技术方解释项目？** 它像企业的 Agent 操作系统：让 AI 不只是会回答，还能安全地做事、留下证据、出错可恢复。
99. **一句话技术价值？** 我将 Agent 从一次性模型调用升级为具备执行状态、证据链、评测闭环和企业治理能力的生产 Runtime。
100. **最大的收获？** Agent 工程的难点不在“让模型调用工具”，而在让不确定模型和外部世界的交互变得可恢复、可验证、可治理。
